编制与公开资料复核日期：2026 年 11 月 13 日，新加坡时间 UTC+8。

### 证据标记与结论边界

〔实测〕指原云 PC 报告已有命令与历史采样支持的结果，不是本次重新检测。〔记录〕指 Dot 附件中的助手陈述，缺少原始工具输出，不能升级为实测。〔用户观察〕指用户直接反馈，支持体验判断但不自动支持技术根因。[A][B][U1]

〔官方〕指适用产品文档的明确说明；不代表本账号所有配置均已核验。〔推断〕须给出依据和理由。〔未确认〕表示证据不足，不能改写成不存在或被永久禁止。技术文档与署名社区意见分别标注，不冒充平台承诺。

### GUI 的核心判断

〔推断〕官方工作流程表明，Dot 优先围绕任务委派和人工接管组织交互；这能解释为什么对话与任务入口更突出，但不能证明界面难用是刻意设计或必要代价。公开资料没有回答其具体 GUI 技术栈、界面投入和设计取舍的内部动机。[O1][O3] 用户的不满意应作为真实体验反馈保留，不能用“主要给 AI 用”将其排除。[U1；评价]

### 为什么不能直接比较数字大小

〔技术说明〕CPU 可见数量表示调度视图，cpu.max 的配额与周期表示 CPU 时间上限；子级还受父级约束。原云 PC 的 4 核是上限，不是独占或保底性能。Dot 缺少对应限制，不能算成“性能为 4 核机器的 2.25 倍”。同样不能把 9.73 GiB 可见内存直接与 8 GiB 硬限制排名。[T1][A][B]

〔复核计算〕Dot 的总量减可用量为 3.40 GiB，约 3,482 MiB，与记录的“已用 195 MiB”不一致。空闲与可用字段、保留空间或采样上下文不同均可能造成差异；原因未确认。两边的 overlay 容量都不能直接代表物理盘规格或独占磁盘性能。[A：#024][B：第 2 节]

## 2 网络访问与远程控制

两套环境已验证的访问路径不同。原云 PC 有用户发起 SSH 的证据；Dot 有用户操作 GUI 的反馈。不能据此推导原云 PC 全网畅通，也不能推导 Dot 的所有非浏览器网络都被禁止。[B：第 3、6 节][U1]

| 访问能力 | 原云 PC | Dot 云电脑 |
| --- | --- | --- |
| 用户远程入口 | 〔实测〕Tailscale SSH 已登录；目标 workbuddy-sandbox | 〔用户观察〕GUI 可操作；独立 SSH 入口未确认 |
| 尾网能力 | 〔实测〕TUN=false，用户态模式在线 | 〔记录〕未建立 Tailscale；没有认证、上线或对端验收记录 |
| 延迟与路径 | 〔实测〕5 次 ping 均经 DERP(sin)，103–106 ms，平均 104.6 ms | 〔未确认〕没有 Dot GUI 往返延迟、帧率或带宽数据 |
| 浏览器与命令 | 〔实测〕尾网连接与部分代理配置；不是全目的地址测试 | 〔记录〕Chromium 配置 browser-proxy:8889；助手命令经临时本地代理成功请求一个目标 |
| 失败现象 | 〔实测〕本地 UDP 探测失败，云端 UDP 可用；具体阻断层未定位 | 〔用户记录〕桌面终端请求失败；命令、错误码及上下文不足 |

来源：原报告第 3、6 节 [B]；附件 #012、#018、#025、#027、#036、#060 [A]；用户 GUI 观察 [U1]。

### 三项必须分开判断的网络能力

〔官方〕Dots 企业安全文档将浏览器访问、代码与 Shell 联网、桌面交互分别控制。〔推断〕因此，同一环境中浏览器成功、终端失败可能涉及代理、策略、DNS、证书或执行上下文差异；目前没有足够证据选出唯一根因。[O2][A：#025—#036]

〔技术说明〕Tailscale 有无需创建 TUN 的用户态代理模式。因此，“没有 TUN”不足以证明所有 Tailscale 用法不可能；但该技术能力也不能证明 Dot 已允许安装、认证或能接受远端连接。Dot 的准确状态仍是未建立、未验收。[T2][A：#012、#018]

〔未确认〕浏览器访问网站的 HTTP 代理，与把云电脑画面传给人的通道，不一定是同一条链路。没有协议与连接证据，不能把 browser-proxy 当作 GUI 卡顿原因，也不能认定 Dot 使用 RDP、VNC 或 WebRTC。[A：#036；推断边界]

〔边界〕104.6 ms 属于原云 PC 的短时 Tailscale 样本，不是 Dot 的延迟，也不是 GUI 响应时间。两边都尚无固定公网入口和生产服务持续可达性的完整证据。[B][C：第 4、6 节]

## 3 数据持久化与持续运行

文件保存、浏览器会话、运行中的进程、网络连接和备份恢复是不同对象。判断持久化时必须明确保留什么、跨越哪种生命周期事件以及如何恢复。以下把存储线索、官方产品能力与本账号实测分别列出。

| 比较对象 | 原云 PC | Dot 云电脑 |
| --- | --- | --- |
| 工作区存储 | 〔实测〕可写层位于 user-data 路径，可见 btrfs/nbd 后端 | 〔记录〕文件能保存到工作区；缺少生命周期测试 |
| 跨使用时段状态 | 〔推断〕后端结构提供保留线索；平台承诺未取得 | 〔官方〕支持保留云电脑状态和跨会话快照 [O1][O2] |
| 具体目录规则 | 〔未确认〕/root、/workspace、/tmp 各事件下的保留规则 | 〔未确认〕具体目录、回收、删除及账号策略适用范围 |
| 浏览器登录态 | 原检查未验收图形桌面及其登录态 | 〔官方〕云浏览器会话独立于个人浏览器，可延续至退出或网站失效 [O1] |
| 进程与连接 | 〔未确认〕Tailscale、SSH 等重启后的自动恢复保障 | 〔未确认〕后台进程、TCP 连接是否随状态恢复而保留 |
| 备份与生产保障 | 未做恢复演练；未确认 SLA、恢复点或平台回收策略 | 未做恢复演练；未确认本账号的恢复点、任意服务 SLA |

原云 PC 的事实定位于原报告第 2、7、8 节 [B]；Dot 文件记录见附件 #039、#042 [A]。表中没有任何一项应解释为“文件永久保存”。

### 应修正的过度概括

〔官方与边界〕“Dot 每次用完一定清空、完全没有跨会话持久化”不符合当前文档。另一方面，状态能延续并不等于任意用户进程始终存活；保存文件或会话与运行不间断、数据库一致性和已有连接不中断并不是同一保证。[O1][O2；后半为技术边界分析]

〔未确认〕企业安全文档对不同配置区分快照保留与删除条件。本例没有核实账号方案、工作区配置和适用政策，所以不把某个企业保留天数套用为该用户的统一文件寿命。[O2]

〔未确认〕原云 PC 的存储挂载与路径名称也不是持久化合同。更大的容量不能证明更可靠、更耐久或具备更好的灾难恢复能力。[B：第 2、7 节；推断边界]

### 对使用方式的影响

〔建议〕两边都将重要源码、文档和交付物保留独立副本，并验证能够恢复。分开测试“关闭客户端后重新进入”“结束一次会话后重开”“平台允许的暂停或恢复”等情景，记录文件哈希、登录态、进程和端口的变化；一次成功只支持该情景，不扩展成无限期承诺。此处是建议，尚未执行这些测试。

## 4 适用场景与选择建议

以下为〔推断／建议〕，依据已验证能力、官方定位和用户需求作出，不是平台认证、性能保证或采购结论。历史状态可能变化，正式迁移前应按实际任务复验。[A][B][O3][U1]

| 使用场景 | 原云 PC 的适配情况 | Dot 的适配情况 |
| --- | --- | --- |
| 用户主导的远程开发 | SSH、配额和 Docker 已检查，直接管理的证据较充分 | 可委派编码并查看结果；独立 SSH 和容器管理未验收 |
| 研究与文件处理 | 可用脚本与工具完成，流程需自行组织 | 符合官方任务范围；具体文档、分析结果仍需验收 |
| Web 开发与预览 | 可作为轻量开发环境；未做本项目端到端测试 | 数独已有用户侧“可玩”的确认；不代表公网发布通过 |
| 长时间人工 GUI 办公 | 当时未确认可用完整桌面，不能直接作为替代品 | 用户体验反馈不佳；应先验证关键人工操作再决定是否采用 |
| 轻量 Docker 实验 | daemon 可查询，具备继续测试的基础 | 当前记录未找到命令；安装与运行权限未确认 |
| 生产数据库或公网服务 | 生命周期、网络入口、备份与恢复保障未确认 | 任意进程长期运行、入站网络、恢复与 SLA 未确认 |
| GPU 训练与游戏串流 | 未有可验证 GPU 或完整图形加速能力 | 未有可验证 GPU 或高帧率串流能力 |

### 更合适的任务分工

〔建议〕需要频繁查看进程、调整环境、调试服务和使用 SSH 时，优先考虑原云 PC 已建立的管理方式；先处理原报告中的启动环境、更新与访问控制问题。该建议不表示其全部软件兼容性或维护措施已经验收。[B：第 5、6、8 节]

〔建议〕需要把研究、文件整理、数据分析或应用开发交给代理，再检查结果、必要时接管浏览器时，Dot 的流程更贴合。但应把成果导出、代码审查、实际运行和结果验收纳入任务，不能仅凭助手“已完成”认定成功。[O3][A：#060、#064][C3]

〔评价〕对于每天主要靠鼠标键盘工作的用户，可操作只是最低条件。交互流畅度、文件查找、窗口切换、中文输入和恢复体验都应成为选用标准。用户对 Dot 的负面评价足以说明当前体验未满足其需求；没有两边同场景的 GUI 测试，不能断言原云 PC 的 GUI 更好。[U1][B]

### 不宜当作唯一存放位置

〔建议〕两边都不应在缺少恢复验证时承担唯一文件仓库。生产托管与长期无人值守网络接入，也应另行确认生命周期和支持范围；本报告没有证明它们永远不能做到，只说明当前证据不足。[A][B][O2]

## 5 Dot GUI 的定位与设计取舍

### 官方明确说明了什么

〔官方〕OpenAI 将 Dot 描述为可在对话间继续工作的代理，能够研究、分析、制作文件和开发软件。产品入口围绕提出任务、查看进展与结果，以及在需要时由用户介入组织。[O3]

〔官方〕用户可以打开云电脑查看，但打开不等于获得控制；选择 Take over 后可用鼠标键盘，完成后 Return control。网站登录也允许用户接管，完成登录或验证后交还控制。[O1]

〔用户观察〕用户明确表示自己能在 GUI 上操作，同时认为界面简陋、使用体验很差。该反馈证明人工入口对用户具有实际用途，但没有提供根因所需的性能记录或逐步复现信息。[U1]

### 从事实到设计解释

| 解释 | 依据与推断理由 | 证据强度与限制 |
| --- | --- | --- |
| 任务委派优先 | 官方强调代理推进工作，人工操作以查看、接管、交还出现；因此推测长期人工桌面不是首要交互模式 | 〔推断〕有流程依据；内部优先级与投入比例未公开 |
| 接管时明确控制权 | Take over / Return control 形成交接；轮流控制有助于减少人和代理同时输入的冲突 | 〔推断〕交接机制属官方事实；是否为实际设计原因未确认 |
| 保持环境一致 | 简化可变桌面组件通常有利于测试、维护和重现任务 | 〔弱推断〕一般工程假设；没有证据证明 Dot 用此原则决定界面 |
| 控制成本或分阶段完善 | 较轻的桌面可能降低维护或资源成本，功能也可能尚在完善 | 〔未确认〕没有成本、路线图或团队说明，不能写成事实 |

前两项推断依据 [O1][O3]；后两项仅列为候选解释，不参与平台事实结论。现有资料无法回答“为什么不把 GUI 做得更好”的内部决策，也不能证明其故意降低人工操作体验。

### 产品定位不能替代可用性要求

〔评价〕以代理为主要执行者，可以解释界面为何突出任务与结果，却不能成为输入不可靠、操作难发现或交接难理解的免责理由。既然官方提供人工接管，用户完成登录、检查文件、纠正操作和恢复任务，就需要可理解、可预测的界面。[O1][U1；评价依据]

〔边界〕安全控制与界面友好并不互斥。更清楚的控制权提示、文件入口和错误说明，可以在不扩展用户权限的情况下改善体验；这是产品建议，不代表这些能力当前全部缺失。也没有证据支持“简陋界面一定更适合 AI”这一说法。[O2；建议与推断边界]

## 6 GUI 体验差的候选原因与核验

〔用户观察〕目前已知的是总体体验差、界面简陋。下表列出的是需要区分的候选问题，不是已经在用户设备上发现的五项故障。[U1]

| 问题类别 | 如果出现该现象 | 需要核验的证据 |
| --- | --- | --- |
| 交互与信息布局 | 不容易找到文件、应用或下一步操作 | 实际完成任务的步骤数、误操作位置、界面状态 |
| 控制权与输入 | 点击无反应、焦点错误或快捷键失效 | 接管状态、前台焦点、按键事件、是否与代理交接重叠 |
| 画面传输与客户端 | 拖动卡顿、文字发糊、滚动断续 | 帧率、分辨率、带宽、丢帧及客户端负载 |
| 云端应用与资源 | 某个应用启动、处理或保存特别慢 | 应用耗时、CPU 节流、内存压力、磁盘延迟 |
| 系统集成 | 中文输入、剪贴板、缩放或重连不顺畅 | 具体输入法、复制方向、缩放比例及重连前后状态 |

### 延迟不能只归因于一个数字

〔技术资料〕Microsoft 的远程桌面诊断将画面端到端延迟分为服务端编码、网络传输、客户端解码和呈现，并指出应用或虚拟机资源造成的慢，需要结合其他指标诊断。这里借用的是分析方法，不是确认 Dot 采用 Azure Virtual Desktop 或 RDP。[T3]

〔推断〕从一次人工按键到看到结果，还可能涉及输入传送、应用处理、画面生成及客户端显示。因此，“CPU 看起来多”“没有可见 GPU”或“存在 HTTP 代理”都不足以单独解释体验差。Dot 的传输协议、编码方式、调度策略和连接路径均未确认。[A：#024、#036][T3]

〔社区个案〕Hacker News 的相关帖子中，用户 slurpyb 也对交接体验表达不满，但没有给出复现步骤和量化指标。这可说明存在其他个体的类似意见，不能代表用户总体，也不能证明 OpenAI 的设计意图或本例故障原因。[C1]

### 可执行的体验验收建议

〔建议〕选择一个简单页面和一个实际工作应用，分别记录接管、输入、滚动、文件打开与交还控制的完整操作；用相同窗口大小和网络条件观察按键到回显时间、失败次数和任务完成步骤。再区分只有某个应用慢，还是整个桌面交互都慢。

〔建议〕优先改善控制权提示、清楚的文件浏览与下载入口、可理解的失败信息、中文输入和剪贴板，以及缩放和重连后的状态反馈。验收目标应来自用户实际任务；本报告不编造帧率、延迟阈值或已测得的优化收益。
