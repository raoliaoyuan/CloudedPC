-5 登录报错的原因与处理建议
-Node.js 与 yargs 的模块错误
-触发入口是 /root/.bashrc.d/50-node 第 2 行的 ng completion script。它在每次交互式 shell 初始化时运行 Angular CLI 的补全生成。第 1 行加载的 nvm-lazy.sh 把 Node 22 的 bin 目录追加到 PATH 尾部，系统 /usr/bin/node 仍排在前面。
-检查发现系统 Node 是 18.19.1，而 NVM 中 Angular CLI 21.1.3 的 yargs 18.0.0 要求 Node ^20.19.0、^22.12.0 或 >=23。用两个 Node 可执行文件分别 require 同一 helpers.mjs：Node 18 返回 ERR_REQUIRE_ESM，Node 22.13.1 成功。该隔离验证复现了截图中的错误，明确支持“运行时选择不一致”这一原因。[5]
-建议：先统一交互终端、SSH 非交互命令及服务进程的 Node 版本与 PATH，再按实际需要启用 Angular 补全。优先修正环境入口，不直接修改第三方 node_modules 文件；随后在新会话里验证 node、npm、ng 的实际路径及版本。
-pyenv command not found
-触发入口是 /root/.bashrc.d/60-python 第 108 行的 eval "$(pyenv init -)"。/root/.pyenv/bin/pyenv 确实存在，使用绝对路径能返回版本；其 Python 3.11.1 也能运行。但是默认 SSH PATH 不包含该 bin 目录。
-建议：在调用 pyenv init 前正确设置 PYENV_ROOT 与 PATH，并加上 command -v 检查。脚本中还有依赖 CloudStudio 环境变量的目录、软链接和编辑器设置逻辑，应区分平台终端与普通 SSH 会话，避免把平台初始化无条件带入所有 shell。
-mv cannot stat 空路径
-触发入口是 /root/.bashrc.d/80-rust 第 4 行：当 /workspace/.cargo/bin/rustup 不存在时，尝试移动 command -v rustup 的结果。默认 PATH 找不到 rustup，命令替换为空，于是出现截图中的 mv 空路径错误。实际 /root/.cargo/bin/rustup 文件存在。
-建议：先检查源可执行文件是否存在及目标目录是否需要迁移，并让初始化可重复执行。更稳妥的方案是修正 CARGO_HOME/PATH 或遵从平台的工具链持久化约定，避免每次登录都移动工具。
-修复后的验收条件
-重新打开 SSH 交互会话应无上述三条报错；非交互执行 node --version、npm --version、python3 --version 应符合预期；pyenv 和 rustup 在需要的会话内可定位。还需验证平台编辑器和后台服务没有因 PATH 调整使用到错误运行时。本次没有改动这些文件，也没有执行包含移动和写入操作的完整启动脚本。
