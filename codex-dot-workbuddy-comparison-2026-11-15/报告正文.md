# Codex Dot对比 Workbuddy云PC对比分析报告及GUI体验分析

**检查对象　Codex Dot 云电脑与本项目 WorkBuddy 托管 Linux 容器**

修订日期：2026 年 11 月 15 日，新加坡时间 UTC+8。WorkBuddy 数据采样于 11 月 10 日；Dot 配置主要来自 11 月 11 日聊天记录。网页说明于本次修订时重新核对。本次未重新连接目标环境实测。

本报告比较两套环境的资源、开发能力、网络入口、数据保留和人工操作体验。当前证据支持：WorkBuddy 的容器管理与远程开发入口更可核验；Dot 已有人工 GUI 操作及应用预览的用户确认。两边缺少同条件性能与桌面体验测试，因此不作算力、安全性或 GUI 优劣排名。[W1][W2][D1][U1]

| 开发与接入 | 数独预览可用；可人工接管；独立 SSH 未验收 | 容器内部 Docker 可查询；Tailscale SSH 登录成功 |

## 1 比较对象与证据口径

### 名称与范围

标题沿用项目中的“Codex Dot”称呼；OpenAI 官方资料使用 dots，并将其与 Codex、ChatGPT Work 分列。本文简称 Dot，比较其自有云电脑；不把委派的 Codex Cloud 仓库环境、用户连接的个人电脑混为同一实例。[O3][O1]

“Workbuddy 云 PC”在本文特指已检查的 WorkBuddy 托管 Linux 容器。DMI 显示 Tencent Cloud 与 CVM，容器检测及进程支持容器形态；多处 sysboxfs、UID 映射等支持“具有 Sysbox 特征”的推断。具体外层运行时版本与实例套餐未确认。容器管理员权限不等于腾讯云 CVM 宿主管理权限。[W1：第 2、8 章]

两边都涉及代理执行工具。WorkBuddy 的 CodeBuddy 组件已有进程证据，不能因本文突出 SSH 就把整个 WorkBuddy 产品描述为只供人手工操作。本报告也不比较模型质量、订阅价格或全部产品功能。[W1：第 5 章；范围界定]

### 必须统一比较口径

〔技术〕cgroup 层级中，子级仍受父级限制。CPU 配额除以周期描述 CPU 时间上限，并非独占或保底算力。WorkBuddy 的叶级显示 max，也不能覆盖父级限制；Dot 没有对应证据，不能计算为其算力是 WorkBuddy 的 9 / 4 倍。[T1][W1：2.2]

〔复核计算〕Dot 的 62.94 − 59.54 = 3.40 GiB，约 3,482 MiB，与记录的“已用 195 MiB”口径不一致。字段、挂载或采样时点差异都是候选解释，原因未确认。WorkBuddy 可见容量较大，也不足以证明独享容量、IOPS 或持久性更好。[A：#024][W1：第 3 章]

〔未确认〕两边均无代表性任务基准、持续吞吐或完整 GPU 验收。工具环境的 CPU 也不能用于推断代理模型的推理硬件。[A][W1；推断边界]

来源：[A：#012、#018、#025、#027、#036、#060][W1：第 7 章][W2：第 3、6 章][W3][U1]。尾网 SSH 成功与容器内 OpenSSH 配置是两组证据，不能直接拼成“该次连接必经容器 sshd 22 端口”。

### 路径不同不能直接解释所有访问差异

〔记录〕Dot Chromium 的 browser-proxy:8889 是浏览器出站配置线索；助手命令工具的 127.0.0.1 临时代理是另一个执行上下文。桌面终端失败仍缺同目标、同方法下的错误码及代理配置，不能写成“Dot 所有 Shell 都断网”。这些代理也不是已确认的 GUI 画面传输链路。[A：#021、#025、#027、#036]

〔技术〕Tailscale 提供不创建 TUN 的用户态模式，因此“没有 TUN”不能推出“永远不能接入尾网”。这不代表 Dot 已获准安装、认证或提供入站服务。[T2][A：#012]

〔边界〕WorkBuddy 的公网出口不等于可入站地址，容器通配监听也不等于公网开放。104.6 ms 是一条尾网路径的短时探测均值，不能当作 Dot 延迟或任何 GUI 的按键到画面耗时。[W1：7.1、7.5][W3]

来源：[A：#039、#042][O1][O2][W1：第 3、5、11 章]。文件、会话、进程和备份是不同对象，不能用一个“持久化”标签全部概括。

### 两个常见误判

〔官方与边界〕“Dot 用完就一定清空”不符合文档的状态保留说明；但状态延续不能推出任意数据库持续在线或已有 TCP 连接不中断。企业文档区分不同配置下的快照期限，不能把某一条期限套用为本例所有文件的寿命。[O1][O2；后半为推断边界]

〔实测与边界〕WorkBuddy 的 sync-server 和 user-data 路径是重要线索，但同步可能复制修改或误删，本身不是已验证的可恢复备份。会话文件存在、日志有发送连接，也不能证明云端完整保留或可随时导出。[W1：第 3、11 章；后半为技术判断]

〔建议〕分别记录正常重连、平台支持的暂停恢复、重启或重建三类事件中的文件哈希、浏览器登录态、进程、监听端口和恢复耗时。重要源码及交付物另存独立副本；这些演练尚未执行。

## 6 权限边界与运维责任

| 维度 | Codex Dot | WorkBuddy 云 PC |
| --- | --- | --- |
| 账号与授权 | 〔官方〕按拥有者连接与适用动作规则工作；实例身份详情不足 | 〔实测〕root 为容器管理员；ubuntu、user 可免密码 sudo |
| 隔离证据 | 缺完整 id、capabilities、namespace 与 seccomp 样本 | 有 UID 映射、namespace、seccomp 与设备限制证据；宿主对照不足 |
| 网络控制 | 〔官方〕浏览器、代码联网与桌面交互分项控制 | 已检查容器 INPUT 链无来源限制；外层控制与完整 nftables 未核实 |
| 更新维护 | 缺完整补丁与维护责任记录 | 发现更新积压与运行时维护问题；不等于已证实可利用漏洞 |
| 日志审计 | 本账号完整记录范围与保留期限未确认 | 观察到日志发送；常规认证与审计日志存在缺口 |

来源：[O2][A：#012、#021、#024][W1：第 6—11 章]。本章比较证据与管理边界，不提供安全评级。

### 管理权限不等于宿主控制权

〔实测〕WorkBuddy 的容器 UID 0 映射到直接外层的 UID 100000；内部 Docker socket 由容器内 dockerd 监听。它们支持“容器内可管理、外层仍受约束”的判断，不能据此声称已获得 CVM root。切换到带免密码 sudo 的 user 或 ubuntu，也不构成可靠低权限边界。[W1：6.2、8.3、8.4]

〔未确认〕有限只读检查没有证实容器逃逸，但不能证明所有路径都已阻断。Dot 的受限陈述同样不能代替隔离审计。两边证据深度不同，不能以“问题列得更多”判定 WorkBuddy 更危险，或以“看不到内部”判定 Dot 更安全。[W1：第 10 章][D1：第 7 章；评价边界]

### 责任如何划分

〔建议〕平台负责核实宿主与外层运行时补丁、租户隔离、入口策略、回收与备份规则；用户负责明确任务授权、控制项目依赖和验收交付物。WorkBuddy 的内部管理权限增加可检查和可调整范围，也需要相应运维；Dot 应优先取得可导出的日志、成果和清楚的失败说明。具体合同责任尚未核实。[W1：第 13、14 章][O2；建议]

## 7 适用场景与任务分工

以下是基于已有能力的〔推断与建议〕。两边都未完成生产托管和长期恢复验收，也没有同负载性能测试，不能视为采购或容量保证。

| 使用场景 | Codex Dot 的适配判断 | WorkBuddy 的适配判断 |
| --- | --- | --- |
| 委派研究与文件处理 | 官方任务方式相符；应验收文件与结果 | 有代码及预览组件基础；代理完成质量未在本比较测试 |
| 直接管理开发环境 | 独立 SSH、权限与安装范围待确认 | 已有 SSH 与内部 Docker 证据，更便于继续开展直接管理 |
| Web 开发与预览 | 数独已有用户侧结果确认 | 具备开发环境；本项目没有同一应用端到端对照 |
| 轻量容器实验 | 命令、安装与运行权限待核验 | 内部 daemon 可查询；具体镜像与负载仍需测试 |
| 长时间人工 GUI 办公 | 用户明确不满意，应先完成关键任务体验验收 | 完整桌面尚未验证，不能直接推荐为更好替代品 |
| 生产数据库与公网服务 | 生命周期、入站、恢复与 SLA 不足 | 同样须验收；开发权限与磁盘视图不构成生产保障 |
| GPU 训练或游戏串流 | 无已验证 GPU 与高帧率能力 | 同样无已验证能力 |

依据：[A：#024、#060][U1][W1：第 2—5 章][W2：第 6 章][O3]。

### 对本项目的建议

需要持续查看进程、调整工具链、调试服务时，可优先使用 WorkBuddy 已验证的远程入口，并先处理启动脚本、访问控制及恢复缺口。需要把成果型任务交给代理推进、再审阅结果时，Dot 的工作流程较契合。这是对已有入口的选择，不是认定另一产品没有相应能力。[W1][O3；推断]

需要整天用鼠标键盘操作时，应先取得两边可用桌面、中文输入、文件操作与重连的同场景结果。当前最明确的 GUI 结论只有 Dot 的负面用户反馈，以及 WorkBuddy 缺少可比测试，不能给出胜负评分。[U1][W1：4.3]

## 8 GUI 工作方式与设计解释

### 已知事实与仍待解释的问题

〔官方〕Dot 云电脑可查看，人工控制需使用 Take over，完成后 Return control；网站登录可由用户介入。〔用户观察〕用户确实能操作，但认为界面简陋、使用体验很差。两者并不矛盾：有操作入口不等于好用。[O1][U1]

〔实测〕WorkBuddy 当时存在桌面相关软件包，但没有发现运行中的 Xorg、Xvfb、VNC、RDP、GNOME 或 XFCE 会话。平台终端、文档预览和按需编辑器不等于已验收的完整桌面。因此，本节不把 WorkBuddy 画成传统远程桌面来作优越对照。[W1：4.3、5.2、5.4]

| 解释或假设 | 依据和推断理由 | 判定 |
| --- | --- | --- |
| Dot 交互优先围绕代理任务 | 官方强调持续推进工作，人工流程以查看和交接出现 | 〔推断〕解释交互重心；不能证明长期桌面被排除 |
| 明确交接有利于减少输入冲突 | 人与代理轮流取得控制，可避免同时操作同一界面 | 〔推断〕工程理由成立；内部决策动机未公开 |
| 界面简化是为降低成本 | 缺成本、资源开销与团队说明 | 〔未确认〕不作为结论 |
| 简陋界面更安全或更适合 AI | 缺直接设计与效果证据；权限控制不必要求低可用性 | 〔未确认〕不能用来解释或正当化体验差 |

前两项依据 [O1][O3]；后两项仅是被排除为定论的猜测。公开材料没有回答团队为何未提供更友好的 GUI，也没有提供改版时间表。

### 人工接管需要达到什么标准

〔专家与评价〕Jakob Nielsen 的可用性原则强调系统状态反馈、用户控制和错误恢复。用于本场景，用户至少需要知道谁在控制、操作是否生效、如何退出或恢复。这里是评价准则，不是对 Dot 已完成的用户研究，也不表示每一项功能当前缺失。[H1]

〔评价〕“以代理为主”能解释交互组织方式，不能替代接管环节的可用性要求。界面是否美观与输入是否可靠、文件是否容易找到应分开评估；增加清楚的状态和错误说明通常不要求扩大权限。[U1][H1；建议]

## 9 GUI 体验问题与定位方法

用户只明确了总体体验差与界面简陋，未提供具体帧率、延迟或逐项故障。下表是〔诊断假设与建议〕，不是已发现的故障清单。[U1]

| 待区分的问题 | 可观察的现象 | 需要的证据 |
| --- | --- | --- |
| 信息组织 | 找不到文件、应用或下一步 | 目标任务、操作步骤、搜索路径、误操作位置 |
| 控制权与输入 | 点击未生效、焦点或按键不符 | 是否已接管、前台焦点、输入回显、交还时点 |
| 画面与传输 | 滚动断续、画面模糊、拖动卡顿 | 同条件录像、分辨率、帧率、丢帧、客户端与链路数据 |
| 云端资源与应用 | 单个应用或操作耗时明显 | 应用耗时、CPU 节流、内存压力、I/O 等同期记录 |
| 系统集成与恢复 | 中文输入、复制粘贴或重连不顺 | 输入法与客户端版本、复制方向、重连前后状态 |

### 延迟链路需要分段判断

〔技术〕Microsoft 的远程桌面诊断把画面延迟分成编码、网络、解码与呈现，并要求结合应用和虚拟机指标。本文借用这一分解方法；不据此认定 Dot 采用 RDP、Azure Virtual Desktop 或某种编码器。[T3]

〔推断〕从按键到看到结果，还需考虑控制权、输入转送和应用处理。因此可见 CPU 多、缺少可见 GPU、存在 HTTP 代理，均不足以单独解释体验差。WorkBuddy 的尾网 RTT 也不能补入 Dot 的延迟链；两边缺少同路径、同工作负载测量。[A：#024、#036][W3][T3]

### 社区反馈与专家意见的适用范围

〔社区个案〕Hacker News 的 slurpyb 在相关帖子中批评任务交接体验，但没有可复核的性能数据。它说明有其他个体表达不满，不能代表社区共识，也不能与本用户记录合成平台故障率。帖子中的证书猜测不用于证明本例 TLS 行为。[C1]

〔专家意见〕Simon Willison 的 Showboat 与 Rodney 文章强调提供演示和命令证据，适合用于验收代理交付；他关于 2025 年 Codex 联网的文章讨论提示注入和外泄风险，不能说明当前 Dot GUI 简陋的原因。[C3][C2]

## 10 后续验收与改进顺序

本章为〔建议〕，未在两套目标环境执行。优先级表示对比较和使用决策的影响，不代表已发现漏洞；不需要先变更目标系统才能理解本报告。

| 优先级 | 工作项 | 可复核的完成判据 |
| --- | --- | --- |
| P1 | Dot GUI 最小任务复现 | 记录打开、接管、输入、文件操作、交还及重连的步骤和结果 |
| P1 | 两边的数据恢复 | 明确目录与事件；文件哈希可核对，独立副本实际可恢复 |
| P1 | Dot 实际资源限制 | 取得可读的限制层级与执行上下文；失败时保留错误及未知 |
| P2 | 同条件资源与 GUI 对照 | 同一任务、输入文件、客户端、分辨率与网络条件，记录重复结果 |
| P2 | WorkBuddy 管理保障 | 核实工具链修复、入口来源、认证日志及服务恢复方式 |
| P2 | Dot 访问差异 | 同一 URL 与方法，保留浏览器、终端、工具路径的错误码和配置 |
| P3 | 生产与长期服务能力 | 单独验收入站、回收、备份、恢复与服务承诺 |

依据：[W1：第 13、14 章][D1：第 9 章][U1]。WorkBuddy 如没有可用桌面，应先记录该前提缺失，不用命令行延迟替代 GUI 数据。

### GUI 验收的具体安排

〔建议〕选取用户实际需要的一个任务，例如找到并打开文件、输入一段中英文、保存后确认结果。再增加一次接管与交还、一次断开后重新进入。记录完成率、误操作或重试次数、任务用时、按键到可见结果的时间；有可靠工具时再记录帧率和链路指标。

〔建议〕先分清“找不到入口”和“动作发出后等待很久”，再判断只有某个应用慢还是整个界面慢。对比时固定客户端版本与窗口大小，多次重复并保留样本数量；预先约定符合用户任务的目标，不事后拼凑一个通用评分或编造改善百分比。

### 界面改进建议

〔建议〕优先核验并改善控制权状态与焦点提示、文件打开及导出入口、中文输入和剪贴板、失败后的重试说明、重连后的任务状态。每项建议都应以实际问题复现为前提；不把它们写成平台已承诺的路线图。[H1][U1]

对本项目，保留 WorkBuddy 的直接管理通道与 Dot 的任务委派流程，各自按已有证据使用；待补齐资源、持久化和 GUI 同场景结果后，再更新选择结论。
